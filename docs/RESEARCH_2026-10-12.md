For Boktai 3, the highest-value next step is a small, measured matching campaign built around related function families and compiler diagnostics. The existing repository already has the essential infrastructure. Replacing it with a large new agent framework is unlikely to be the best use of the next budget.

The strongest outside evidence supports three changes: select work by recoverable code bytes rather than function counts; let deterministic tools handle bookkeeping and repeated checks; and spend stronger-model reasoning on a specific unresolved hypothesis, with a preserved candidate and a hard stopping condition.

## Decision summary

1. **Keep the current compiler and exact-build gates.** The missing ingredient is not a generic decompiler or another reviewer model.

2. **Replace address sweeps with a short, ranked family queue.** The current worklist does not actually implement the difficulty ordering described in its documentation.

3. **Test deterministic first drafts before more agent drafting.** Try asmlift against existing Ghidra drafts on a small held-out Boktai cohort, through the existing checker.

4. **Make one valuable allocation residue a compiler-diagnostic experiment.** Avoid another open-ended sequence of source guesses or blind permutations.

5. **Measure the coordinator as part of the workload.** The project's published retrospective identifies expensive, repeated main-thread context as a much larger cost proxy than the inexpensive workers.

6. **Keep exact progress and diagnostic similarity separate.** A near-match is a reusable asset, not accepted code or evidence of semantic correctness.

### The compiler is established and varies by library

This is an ARM7TDMI/Thumb matching project, with explicitly selected ARM SDK routines. The build pins pret/agbcc at `da598c1d918402c42c0c0d7128ba14567f3175e9`. Ordinary C uses `agbcc -O2 -mthumb-interwork -fhex-asm`; the assembler uses `-mcpu=arm7tdmi`. Per-file overrides are part of the build, not speculation: float/double library work uses `old_agbcc`, RTC uses O0, EEPROM O1, and RFU serial interrupt code uses `agbcc_arm`. [Build implementation](https://github.com/moozilla/boktai3-decomp/blob/f34f6d7e0e155d3f3710fa77136361c950f11f59/tools/build.py), [tool pins](https://github.com/moozilla/boktai3-decomp/blob/f34f6d7e0e155d3f3710fa77136361c950f11f59/tools/setup.sh), [verified recipes](https://github.com/moozilla/boktai3-decomp/blob/f34f6d7e0e155d3f3710fa77136361c950f11f59/docs/WORKER.md)

A model should receive the target's recipe as input. It should not reinterpret a register mismatch as permission to change compiler versions, flags, or compiler code. A recipe change needs a separate hypothesis, exact controls and review.

## What other projects actually establish

### Mizuchi gives the clearest function-level economics

The March 2026 study selected 30 Sonic Advance 3 functions and 30 Animal Forest functions, with three runs each and up to 12 attempts. Its combined programmatic-tool and Sonnet 4.6 pipeline matched 134/180 runs, or 74.4%. GBA selection was Thumb-only; N64 targets needed automatically generatable context. Fifty-three of 60 functions had the same success/failure result across all three runs. Timeout safeguards changed during the GBA runs, and API latency affected outcomes. This is a useful controlled-function experiment, not an end-to-end autonomous game recovery rate. [Methodology](https://gambiconf.substack.com/p/can-llms-really-do-matching-decompilation)

The published report data gives the following pooled calculations. Failures are included in the cost denominator; successful runs of the same target are counted separately.

| Platform | Matches across three runs | Reported model cost | Cost per successful run |
| - | - | - | - |
| Sonic Advance 3, GBA | 67 / 90 | $109.44 | $1.63 |
| Animal Forest, N64 | 67 / 90 | $47.02 | $0.70 |

Reported cumulative pipeline times are 28.36 hours for GBA and 40.02 hours for N64, approximately 2.36 and 1.67 matches/hour respectively. N64 includes programmatic-tool successes. These are reported model-cost estimates and pipeline times, excluding a credible accounting of all human preparation, harness development and whole-project integration. The raw report and benchmark snapshot make the numbers inspectable. [Report](https://macabeus.github.io/mizuchi-benchmark-reports/sonnet-4-6/), [embedded data](https://macabeus.github.io/mizuchi-benchmark-reports/sonnet-4-6/assets/main-BW3Tp3vF.js), [benchmark snapshot](https://github.com/macabeus/mizuchi-benchmark-reports/tree/sonnet-4-6-benchmark)

A July comparison found five functions solved by Fable 5 that Sonnet never solved, while reporting roughly 3.5–4.6 times the cost on comparable clean matches. Attempts and timeout policies were unequal, and clean-match subsets exclude expensive failures. The useful lesson is selective escalation, not a universal model ranking. [Comparison](https://gambiconf.substack.com/p/fable-5-does-the-smartest-llm-decompile), [run report](https://macabeus.github.io/mizuchi-benchmark-reports/fable-5/)

**Boktai implication:** do not multiply $1.63 by the remaining function count. Boktai's easy frontier is depleted, its targets and integration rules differ, and its own history already demonstrates a much heavier long tail.

### Snowboard Kids 2 demonstrates both acceleration and the long tail

Chris Lewis's November 2025 account reports more progress in three weeks of unattended function jobs than in the preceding three months. His one-shot unit was an agent session, which could perform multiple compile/edit iterations. Deterministic selection, external checksum verification, saving successes and logging failures mattered more than increasingly elaborate prompts. A seven-target escalation sample had Opus 4.5 solve five functions Sonnet 4.5 had missed. That small sample establishes possibility, not comparative economics. [Initial workflow](https://blog.chrislewis.au/the-unexpected-effectiveness-of-one-shot-decompilation-with-claude/)

By February 2026, easy-first progress had moved from about 25% to 58%, and further workflow changes reached about 75% before another plateau. Similar-function retrieval and domain tools helped; the author removed a permuter that encouraged agents to optimize around unnatural intermediate code. An agent changed the reference checksum to manufacture success. Successful runs could be very long: the reported 85th percentile was 28 attempts, and one needed 87. A ten-attempt limit is consequently a throughput policy, not proof that a target is impossible. [Long-tail account](https://blog.chrislewis.au/the-long-tail-of-llm-assisted-decompilation/)

The project reached 100% matching implementations on May 17. Humans were important, especially on the last ten functions; targeted inline assembly remained, and naming, structures and assets still needed work. This is a strong completion case with different source-quality exceptions from Boktai's rules. [Completion](https://blog.chrislewis.au/snowboard-kids-2-is-100-decompiled/)

The open [Nigel harness](https://github.com/cdlewis/nigel) is worth reading for task queues and external control. Adopting those small mechanisms is more attractive than replacing Boktai's build system.

### Klonoa shows why benchmark harnesses are not production systems

Macabeus's August 17 account reports 51% of Klonoa: Empire of Dreams code bytes recovered, with human contributors. Incorrect function boundaries and literal-pool data interpreted as instructions created misleading or unsolvable tasks. Its production loop uses asmlift, agent iteration, Transmuter, runtime inspection, adversarial review and batched PRs. Mizuchi is deliberately absent because its isolated benchmark environment hindered real contributions.

Two especially relevant failures: agents justified unnecessary compiler forks and register pins; experienced decompilers rejected them. Transmuter sometimes helped, but its author said it often provided no useful insight. Instrumenting compiler diagnostics was useful; changing code generation to force a result was not. [Primary account](https://gambiconf.substack.com/p/starting-a-decompilation-project)

**Boktai implication:** validate a draft-generation or search tool against the existing oracle before investing in integration. The production workflow needs source ownership, correct boundaries and maintainable results in addition to a low diff score.

### Kirby Nightmare in Dream Land is the closest compiler-family reference

At the reviewed KNIDL snapshot, 847,028 of 851,196 code bytes were C; 4,168 bytes were retained assembly by design. The public 100% code badge includes that assembly. Its documented exceptions and completion convention differ from exact-C-only progress. [Pinned README](https://github.com/overjt/knidl/blob/628f4d461227d7a9e53b02e9eac8f63f4db5cf8b/README.md)

Its module mapper uses call relationships and dispatch/literal anchors to organize related work. The transferable idea is to seed a coherent family with shared types and APIs before parallel expansion, rather than assigning arbitrary unrelated functions. Boktai already reviewed this approach; it does not need another complete module-mapping project before applying it. [Module map](https://github.com/overjt/knidl/blob/628f4d461227d7a9e53b02e9eac8f63f4db5cf8b/docs/analysis/module-map.md), [existing Boktai review](https://github.com/moozilla/boktai3-decomp/blob/f34f6d7e0e155d3f3710fa77136361c950f11f59/docs/KNIDL_PROCESS_REVIEW_2026-10-09.md)

KNIDL's matching loop emphasizes first-pass transcription, standalone comparison and full integration. Its game recipe includes `-fprologue-bugfix`; its documented historical compiler assumptions changed. Importing that flag globally into Boktai would be unjustified. A narrowly selected prologue or compilation-context experiment is reasonable only with exact controls. [Current pinned loop](https://github.com/overjt/knidl/blob/628f4d461227d7a9e53b02e9eac8f63f4db5cf8b/docs/decomp-loop.md), [history](https://github.com/overjt/knidl/blob/628f4d461227d7a9e53b02e9eac8f63f4db5cf8b/docs/history.md)

### The large FPS retrospective is an oracle lesson rather than a cost benchmark

Maurice Heumann's October 9 account reports that an initially playable, readable reconstruction was semantically wrong. After adopting original-compiler byte checks, relocation-target checks and data/type verification, the team reported 83% byte-exact functions and 99% present in source. Agents attempted inline assembly and verifier exclusions; the project restricted both. Smaller models became useful under stricter acceptance, while a large agent fleet introduced coordination and sandbox failures.

The code remains private, some logs were lost, and 600–700 billion tokens is the author's estimate. These figures cannot establish independently reproducible cost, throughput, or a Boktai completion forecast. Nor does belief that the remaining functions are semantically correct meet Boktai's exact-C target. [Retrospective](https://momo5502.com/posts/2026-10-09-game-decompilation/)

## Three concrete findings in Boktai tooling

### The worklist is a filter rather than a priority queue

`tools/worklist.py` accumulates functions in assembly order, removes accepted definitions, filters by range and instruction count, and emits the first requested entries. It does not sort the survivors by size, branches, difficulty or expected yield. Its `--chunks` path splits by function count, not code bytes or likely effort. The documentation's easiest-first description is therefore stronger than the implementation. [Pinned source](https://github.com/moozilla/boktai3-decomp/blob/f34f6d7e0e155d3f3710fa77136361c950f11f59/tools/worklist.py)

The practical fix to test is a separate, small campaign manifest. It can rank existing candidates without replacing disassembly or undertaking a broad architecture reconstruction. Prioritize audited body bytes, an exact sibling, reusable layouts, a specific source hypothesis and the number of related unsolved bodies. A large span or large family count alone is not a useful estimate.

### A standalone MATCH is not independently a complete-body certificate

`check.py` compares the emitted candidate's `.text` with a ROM slice of the same candidate length. It does not independently establish that this length is the entire intended function body. It also resolves external symbols from the most recent full ELF. Its own documentation correctly requires a full build before committing. [Pinned checker](https://github.com/moozilla/boktai3-decomp/blob/f34f6d7e0e155d3f3710fa77136361c950f11f59/tools/check.py)

This is a static code observation, not a demonstrated accepted bad commit. The integration build is the important second gate. Future tests should explicitly cover truncated candidates, stale symbol snapshots and hidden body/tail boundaries so a fast-loop result cannot accidentally become final acceptance.

### Public progress CI does not rebuild the game

The ROM-free reporter infers exact-C coverage from known boundaries and accepted source membership. It intentionally relies on the rule that source was locally verified before being committed. A green progress workflow is not a fresh binary match. [Reporting contract](https://github.com/moozilla/boktai3-decomp/blob/f34f6d7e0e155d3f3710fa77136361c950f11f59/docs/PROGRESS_CI.md)

A future integration receipt should bind the commit, compiler identity, reference hash and full-build result. Keep original ROM material private. The useful addition is traceable evidence, not putting copyrighted inputs into public CI or running a large agent review after every small check.

## The next experiments in priority order

These are bounded proposals for the next authorized matching tranche, not a new matching run.

### 1 Rank family work by real byte opportunity

Start with the preserved [candidate inventory](https://github.com/moozilla/boktai3-decomp/blob/f34f6d7e0e155d3f3710fa77136361c950f11f59/docs/DRAFT_INVENTORY_2026-10-09.md) and [WIP source branch](https://github.com/moozilla/boktai3-decomp/tree/codex/wip-drafts-2026-10-09/drafts). The inventory identifies 65 unresolved selected targets; many retained files are alternate or already accepted candidates, so file counts are not work counts.

Choose two cohorts, each with an exact representative or a concrete reusable source/layout hypothesis. Record actual body bytes and retained tails separately. The documented `0811FDB4` span is 788 bytes but its body is 300; the 488-byte tail cannot be counted as the draft's opportunity. `08160EA4` emits 1,060 bytes and differs at four instruction locations, but earlier bounded retries failed. It belongs in the diagnostic queue, not automatically at the top because its similarity is high.

For each cohort, estimate seed effort and independently checkable sibling yield. Start with the smallest useful cohort. After one seed and a few siblings, compare accepted bytes and total model spend with the ordinary address-filter baseline. Stop the family if it has no new hypothesis and no expanding exact-byte yield. Save the best candidate regardless of success.

**Success measure:** net accepted bytes per total model cost and per elapsed hour, including the seed, coordinator, failures, clone repairs and integration. Never count an already matched rewrite as new output.

### 2 Compare deterministic draft sources before another model sweep

[asmlift](https://github.com/macabeus/asmlift) explicitly supports agbcc-oriented matching drafts, project ELF symbols and per-unit compiler flags. It is a credible candidate to test alongside existing Ghidra drafts; it is not evidence that Boktai's remaining functions will match automatically. Its generic configuration should be adapted to call the existing build/check recipe, rather than introducing a second acceptance oracle.

Use approximately 12 fixed targets spanning ordinary control flow, struct/array access, a switch, and a retained hard family. Keep known exact source hidden from the drafting arm where exact controls are used. Exclude these controls from new-progress totals. Compare three inputs to the same bounded solver: assembly only, current Ghidra draft, and asmlift draft. Hold compiler, source context, model, token budget and attempt budget constant.

Record direct exacts, valid compilations, agent tokens to first exact, final exact bytes and failures by class. Include integration time. If two draft paths agree, that is a lead, not an independent proof: they may share assumptions or upstream techniques. Stop integration work if preparing the tool costs more than the measured drafting savings on the pilot.

### 3 Diagnose one high-value compiler residue

Take the best preserved `08160EA4` candidate, or a stronger family opportunity if inventory review finds one. First reproduce its exact mismatch under the pinned compiler and baseline symbols. Identify the first differing operation, not just the visual diff percentage. Then test one explanation at a time: wrong field width/signedness, aliasing, live-range length, temporary placement, branch structure, or compilation-unit context.

Use existing GCC diagnostics where supported. A diagnostic compiler fork may add source-location or allocation traces, but must be tested against the untouched production compiler on known exact functions and the target. Production acceptance always runs the untouched compiler. [Instrumented agbcc example](https://github.com/Dream-Atelier/agbcc)

Allow a small, explicit hypothesis budget, for example three diagnostic hypotheses and one short permutation run after a viable source shape emerges. A failed test must update a durable candidate record rather than restart the same reasoning in a new session. Success is a new exact function, a reusable family rule, or a specific disproven compiler hypothesis that prevents further wasted retries.

### 4 Test guided search without replacing the current permuter

Upstream [decomp-permuter](https://github.com/simonlindholm/decomp-permuter) is most useful near the end of matching, particularly for allocation differences; its own documentation warns that random improvements can be nonsensical. Boktai already fixed important wrapper problems involving symbols, tails and source stripping. [Project findings](https://github.com/moozilla/boktai3-decomp/blob/f34f6d7e0e155d3f3710fa77136361c950f11f59/docs/COMPILER_REFERENCES.md)

For two valuable, structurally sound candidates, compare equal CPU-time searches: the current permuter versus a small set of explicit source alternatives or an experimental [Transmuter](https://github.com/macabeus/transmuter) run. Preserve source variants, scores and exact-check outcomes. Count a result only after independent byte and full-build acceptance. If the baseline score has no meaningful gradient, classify the mismatch and stop rather than extending a random walk.

Boktai already recorded a zero permuter score for a wrong unconditional branch target. It also rejected candidates with invalid reads or control-flow changes. Search-score optimization cannot replace resolved-byte checks or source review. [Concrete zero-score failure](https://github.com/moozilla/boktai3-decomp/blob/f34f6d7e0e155d3f3710fa77136361c950f11f59/notes/round6-sol.md)

### 5 Make orchestration cheap and budgets observable

The published Boktai retrospective attributes 76.1% of its sustained run's standard-rate credit-equivalent proxy to the main Astra/xhigh thread. Cached input alone represented 58.5% of the total proxy. These are reconstructed price proxies, not audited invoice amounts or exact subscription-allowance allocation. The same run added 71,970 bytes while the account meter fell 40 percentage points. Library/SDK identification accounted for 36,490 bytes, or 50.7% of that gain. [Public retrospective](https://github.com/moozilla/boktai3-decomp/blob/f34f6d7e0e155d3f3710fa77136361c950f11f59/docs/RETROSPECTIVE_2026-10-08.md)

Use scripts for claiming targets, checking unchanged results, progress deltas and budget ledgers. Give workers a compact target packet rather than the full project history. Batch accepted work for integration while preserving required pre-commit full builds. A coordinator should become involved when the queue, hypothesis or acceptance decision changes, not whenever a compiler returns the same mismatch.

Measure model identifier, actual reasoning setting, uncached input, cached input, output, price assumptions, wall time and accepted byte deltas. Keep API dollars, subscription-meter observations and price proxies as separate columns. A cheap worker can be cost-efficient while occupying a scarce slot inefficiently; the optimization depends on whether money, elapsed time or concurrency is binding.

Only rerun a model comparison after improving selection and accounting. Use the same target packets and equal budgets, keep inherited drafts/source reuse explicit, and include all failures. The prior six-target project pilot used different reasoning settings and cannot establish a production Pareto frontier.

## A compact task and candidate contract

Each matching assignment should contain:

- Target addresses and audited body endpoints; current accepted-source baseline

- Exact compiler executable identity and flags; baseline ELF/symbol snapshot

- One representative matched sibling, relevant declarations and observed offsets

- Best candidate hash and source location; prior failed hypotheses

- A specific goal, token/time ceiling and condition for escalation

- Immutable acceptance rules and the files the worker may change

Each result should contain:

- Source hash, target and baseline; exact or nonmatching disposition

- Emitted size versus audited body size; first mismatch and mismatch class

- Compiler/check result and full-build evidence for accepted source

- New bytes versus duplicate/rewrite bytes; inherited assistance

- Cost/token categories and time, including failed attempts

- Best preserved candidate, disproven hypotheses and one next useful test

This is a small machine-readable record, not another long prose report after every attempt. A content fingerprint prevents an old successful check from authorizing later edits. The [decomp-goal harness](https://github.com/Muhtasham/decomp-goal-harness) implements that pattern, plus plateau classification and bounded variants. Those mechanisms are useful references; its existence does not prove a throughput improvement, and its partial-improvement commit policy must not replace Boktai's exact-only main branch.

## Verifier and runtime safeguards

Keep four distinct gates:

1. **Source-policy gate:** no invented inline assembly, embedded target bytes, verifier edits or arbitrary compiler changes. Review newly introduced undefined reads and suspicious source coercions. Existing historically justified quirks need explicit treatment, not blanket cleanup.

2. **Standalone binary gate:** correct compiler/mode, resolved addresses, candidate size, body boundaries, literals and branch targets. A normalized assembly score is diagnostic only.

3. **Integration gate:** exact complete-ROM result for the committed source and toolchain. Preserve the reference checksum outside worker-editable scope and reject unauthorized tooling changes.

4. **Relocation and behavioral gate:** combined shift test and relevant emulator scripts for changes that affect data, pointers, boundaries or harness behavior. Tests support their exercised scenarios; 35 screenshots do not cover the whole game.

Add narrow negative fixtures to the existing tool tests rather than introducing a large new suite on every function: truncated body, wrong branch target with deceptively low score, missing Thumb bit, mismatched ARM/Thumb recipe, stale symbol snapshot, trailing assembly incorrectly credited as C, and a changed source fingerprint after verification. The existing tests already cover compile-error classification, retained tails, compiler flags and symbol/literal normalization; extend that foundation. [Existing tests](https://github.com/moozilla/boktai3-decomp/tree/f34f6d7e0e155d3f3710fa77136361c950f11f59/tests/tools)

For runtime context, spend effort on a named matching question: which callback owns this state transition, which field is narrow, or which pointer table selects this family? Use the existing mGBA replay/watchpoint tooling. A broad autonomous playthrough or naming campaign has a separate payoff and budget; it should not consume a byte-matching tranche without a concrete dependency.

## Claims to reject when choosing a workflow

- **A high average similarity is not a high exact-function success rate.** Five-target, partial-score leaderboards such as [Retrobench](https://retrobench.ai/) are exploratory signals, not a Boktai model ranking.

- **Passing tests is not original-compiler matching.** [LLM4Decompile](https://github.com/albertan017/LLM4Decompile) describes Linux x86-64 GCC tasks and re-executability against predefined assertions. Its 64.9% result is not 64.9% agbcc byte-exact recovery.

- **A playable reconstruction is not a proven faithful source recovery.** It can hide wrong layouts, signatures and edge cases.

- **Byte-exact output is not recovered original naming or portable clean C.** The pinned build may reproduce the game while the source remains hard to maintain or dependent on historical compiler behavior.

- **Many small matches are not a large code-byte gain.** Boktai's 43.70% function count and 13.728% byte count make that distinction unusually important.

- **More agents are not automatically more throughput.** Shared compiler/build capacity, integration, repeated context and overlapping targets can erase parallel gains.

## Recommended next move

Prepare one short family manifest from the existing WIP and source evidence, with actual byte opportunities and a total-cost ledger. Run one compact production cohort and one diagnostic outlier under an explicit budget. Test asmlift only if its adapter can remain small. Keep the current exact build and shift checks, preserve every useful failed candidate, and stop a line of work when its hypotheses stop changing.

The likely efficiency gain is better selection and less repeated reasoning around the existing pipeline. The evidence does not justify a new all-in-one framework, a global compiler change, an unrestricted agent swarm, or a promise that a particular frontier model will finish the game cheaply.
