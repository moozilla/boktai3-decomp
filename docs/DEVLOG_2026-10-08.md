# Boktai 3 devlog for October 8 2026

Boktai 3 now rebuilds with **4,789 functions in C**, accounting for **323,090
matched code bytes, or 13.377% of the tracked code region**. This local session
started from 4,145 functions and 220,400 bytes: **644 additional functions and
102,690 bytes**, an increase of 4.252 percentage points. Every accepted match
still reproduces the original Japanese ROM byte for byte.

The most substantial gains came from identifying library source and compiler
variants. We also established a useful connection to Metal Gear Solid's script
system, made script calls observable in the running game, and reconstructed
the low-level solar sensor code. Alongside that work, the project acquired a
working macOS setup, isolated worker checkouts, and public progress tracking.

The existing project supplied the matching pipeline, shiftable data, emulator
replays, text tools, and thousands of matches. This session built on that work;
it did not create those systems from scratch. The later sustained run—from
9.302% to 12.282%—accounts for 422 of the new functions and 71,970 of the bytes.

These are byte-weighted C matching results. They do not describe how much of
the game has been played in the emulator or how many assets have been decoded.
Although 43.22% of the known functions are now matched, short functions count
the same as long ones in that figure. The byte percentage is the more useful
measure of the amount of native code reconstructed.

The first task was making the inherited cloud workflow work locally. The
user-supplied ROM was verified and kept outside version control. Python tools
now use `build/venv`; the pinned compiler, disassembler, assembler, permuter,
and mGBA harness build on macOS. Workers share the ROM, generated assembly,
Python environment, and built tools read-only, while retaining separate build
outputs and candidate source. That separation also made the initial model
pilot independent: workers could not read one another's solutions.

Progress reporting is now registered on
[decomp.dev](https://decomp.dev/moozilla/boktai3-decomp). A GitHub Actions job
produces an address-and-count report using Python, without a ROM or compiler.
It runs when a reviewed batch reaches `main`, or on manual dispatch; individual
worker commits do not each trigger a run. Local exact builds establish matching,
while CI checks the reporting logic and publishes the metadata. The complete
setup and counting policy are in [PROGRESS_CI.md](PROGRESS_CI.md).

The largest matching lesson was that there is no single compiler setting for
every component of the ROM. Ordinary game code continues to match agbcc with
optimization and Thumb interworking. The floating-point runtime instead
matches `old_agbcc -O2`: two contiguous units supplied **40 functions and 5,864
bytes**. Their library source also exposed 18 function starts previously hidden
inside assembly blobs. A compiler-selection cache bug was fixed so changing
the compiler cannot accidentally reuse an older object and give a misleading
result. [LIBGCC.md](LIBGCC.md) records the exact source and linking evidence.

That led into the math library. Historical newlib 1.8.2 fdlibm source, built
with `old_agbcc -O2 -fno-builtin`, matched **22 functions and 11,584 bytes**.
These include trigonometric routines, inverse trigonometric routines, square
root, remainder, and range-reduction kernels. One newer source revision was
close but did not match; a different bracing scope in the older `asin` source
was enough to matter to the compiler. Two adjacent memory primitives added
another 178 progress bytes. Existing ROM constant tables are referenced by
symbols, and source notices and provenance are retained. See
[LIBM.md](LIBM.md).

Other SDK components required their own settings. Fourteen real-time-clock
routines matched at **O0**, adding 1,784 bytes; five EEPROM routines matched
at **O1**, adding 808 bytes. Their differences are supported by compiled bytes,
not a blanket theory that difficult functions must use another compiler.
The details are in [RTC.md](RTC.md) and [EEPROM.md](EEPROM.md).

The biggest single library integration was RFU, the wireless-adapter SDK.
The ROM's `RFU_V1024` identification is backed by exact matches to the
version-1024 implementation reconstructed in pret's pokeemerald project.
Four contiguous C units now cover transport, the link API, serial identification,
and interrupt handling: **145 functions and 18,056 emitted bytes**. Of those,
54 functions were already C. The incremental gain was **91 functions and
16,272 progress bytes**.

RFU also exposed a mixed-instruction-set problem: seven interrupt routines
are ARM code inside what the disassembler had retained as a binary blob.
The build now supports `agbcc_arm` and reviewed ARM/Thumb boundaries without
modifying shared generated files. Three tiny callback trampolines remain
assembly and receive no C credit. Exact source matches give the SDK routines
much stronger names than address placeholders, but do not prove which wireless
features the game exposes to players. [RFU.md](RFU.md) contains the source,
version, layout, and naming evidence.

Game-specific matching continued alongside those libraries. Workers recovered
allocator wrappers, state-machine cases, pointer and field operations, and
related function families. A seven-member counter family contributed 4,088
bytes after a shared source pattern was found. Successful patterns were carried
to siblings instead of repeatedly reconstructing each function independently.
Many remaining near-matches are blocked by register allocation or instruction
ordering; their candidates and failure notes remain available for later work.

The external development-history review produced one concrete architectural
lead: several Boktai script routines correspond closely to the reconstructed
GCL system in Metal Gear Solid. The evidence includes the 16-bit name hash,
command registration and lookup, block execution, and several command IDs.
It does not establish that the games share their whole engine. The dedicated
matching work added **50 functions and 7,024 emitted bytes** across seven rounds,
covering parser and dispatch operations as well as expression, message,
callback, trap, and related support routines. B3-specific differences and
unsolved comparisons are preserved in [MGS_GCL_MATCHING.md](MGS_GCL_MATCHING.md).

SolDec was useful as another comparison point, but is tested for Boktai 1 and
cannot simply be treated as a complete Boktai 3 decoder. This review documented
B3's text operands, pointer-selected variable storage, and distinct length
formats. It also identified a **722-entry actor callback registry**. A bounded,
read-only audit tool checks tables and packet envelopes; a complete bytecode
decompiler and byte-exact decode/re-encode pipeline remain future work.
[PROCESS_REVIEW.md](PROCESS_REVIEW.md) separates supported correspondences
from the historical claims that did not survive inspection.

To connect that static map with gameplay, the emulator harness gained
read-only instruction probes. A joiner connects script command IDs to native
handlers, actor registry keys, and resolved callbacks while checking nesting
and register/stack consistency. The intro replay yielded **698 completed native
calls and 90 actor callbacks**, covering ten distinct native targets and forty
actor targets. This tells us which callbacks actually ran and with what
arguments; it does not automatically identify every on-screen character.

Building those probes exposed an execution-sampling bug. The harness used the
memory-hook PC adjustment between CPU steps, and pending interrupts could
produce phantom observations. Both were corrected. Older execution traces
need regeneration before supporting function-entry claims. The corrected intro
retained all 16 original screenshots, and the shifted-data regression retained
all 35. The existing Centaur input recordings can feed the same replay system;
this is a useful step toward shared human/agent investigation, not a finished
interactive debugger. See [SCRIPT_TRACING.md](SCRIPT_TRACING.md).

The solar sensor provided a small, concrete end-to-end example. Three new C
routines reconstruct initialization, shutdown, and the timer interrupt, adding
**512 exact bytes**. Together with five existing wrappers, they describe how
GPIO reset and clock pulses produce a sampled threshold count. An ordinary
late-game replay exercised four emulator light settings, captured eight memory
snapshots, and probed the result stores. The original and rebuilt ROMs agreed
on every snapshot and probe row. The observed one-count timing variation is
documented; the emulator's input values are raw thresholds, not physical lux.
[SOLAR_SENSOR.md](SOLAR_SENSOR.md) records the protocol, state, and proposed
function names.

Several smaller tooling improvements protect the validity of future matches.
The permuter wrapper now compares resolved addresses consistently, preserves
compact function bodies and inline helpers, excludes retained assembly tails,
and isolates search outputs. A zero permutation score still requires an exact
byte check: one candidate had a branch-target difference despite scoring zero.
Unsafe candidate transformations were rejected. The progress inventory also
gained explicit unmatched boundaries so trailing assembly could not be credited
to a preceding C function. That run's inventory contained 11,068 functions;
discovering boundaries is recorded separately from matching them.

The final integrated ROM passed the original SHA-1 check, all **35 screenshot
comparisons** with data moved by 64 KiB, **36 local tooling/context tests**, and
the progress Actions workflow. ROMs, generated assembly, emulator traces,
screenshots, and unfinished candidates remain untracked. That run's matching
state was commit `5ff44e3`, following eight reviewed integration PRs.

The session improved both the native source and the evidence available for
understanding the game, but its allowance efficiency was disappointing. The
sustained run stopped on budget before reaching 20% matched code. The
[retrospective](RETROSPECTIVE_2026-10-08.md) examines the expensive main-thread
context, weak model-cost accounting, and work allocation. The practical next
step is a smaller measured matching run focused on library/source reuse and
high-yield families, with bounded architecture work and explicit cost reporting.

## Matching follow-up and closeout

The user authorized a new push from `5ff44e3` toward 20% code while preserving
20% remaining plan usage. Sol 6.1 workers used high reasoning, with bounded
Astra-low escalations for blockers. Four reviewed integration batches added
**116 functions / 22,708 progress bytes** (22,732 emitted bytes), ending at
`8c2c818` through PRs #9–#12. The [matching report](PUSH20_2026-10-08.md)
records each batch and distinguishes emitted bytes from progress spans.

Fresh initialization and allocation routines, real struct layouts, and a few
larger straight-line math/setup functions produced the accepted source. Clone
sweeps and prolonged register-allocation tuning had weak yield. Reviewed
function boundaries separated retained Thumb bodies from adjacent matches,
keeping the byte denominator fixed. Source review also repaired three
unsequenced assignment/read patterns without changing the matched bytes;
those repairs receive no new-byte credit.

Every combined source batch passed the full ROM check and all 35 shifted-data
screenshots. The broad tooling/context suite ran for the first two batches;
it was not repeated for the last two C/metadata batches. The final restored
build printed `build/boktai3.gba: OK`, and the main Progress Action succeeded
for `8c2c818`. No ROM, generated assembly, emulator dumps or nonmatching source
was committed.

The account meter fell from 32% to the 20% remaining floor. Matching stopped
with **163,705 bytes still needed** for the requested target. The last Sol
attempt at 0811FDB4 stopped after three nonmatching drafts; its body is only
300 bytes, with a separate 488-byte retained tail. The final Astra escalation
stopped at its usage check before attempting that candidate. All accepted work
is merged, workers are finished, and unfinished drafts remain in local isolated
checkouts. Documentation closeout adds no matching-byte credit.


## October 9: bounded existing-draft rescue

The user authorized finishing retained drafts for at most one hour or until
15% plan usage remained, without new agents or new targets. An exhaustive WIP
audit identified 113 unmatched targets in 435 C files and checked one
representative per target plus 68 distinct existing alternates. Two previously
exact candidates had been overlooked. Correcting clone constants, sizes,
strides and field offsets finished most of the accepted queue. Ordinary
bitfield assignments replaced explicit reads of uninitialized full words;
unused upper bits are padding. One previously blocked math/setup draft also
became exact. The resumed Astra-low worker added no matches in its capped
FDB4, motion and bit-store attempts.

The combined batch adds **48 functions / 3,724 exact bytes**, reaching
**323,090 / 2,415,354 bytes (13.377%) and 4,789 / 11,081 functions**. The RTC
candidate contributes 156 bytes; its separate 308-byte alarm body remains
assembly. Adding that reviewed boundary prevents false credit from the old
464-byte span. No source chunks or nonmatching C receive progress credit.
The 20% target is still short by **159,981 bytes**.

The [inventory](DRAFT_INVENTORY_2026-10-09.md) records the 65 remaining
nonmatching targets, candidate paths and hashes. Those sources remain local
and ignored, so they cannot be reconstructed from a fresh GitHub clone.
Partial candidate retention would require an explicit exception to the current
no-nonmatching-C commit rule. No new partial-reporting feature was built.
Validation is consolidated into one full-ROM build and the required combined
35-screenshot shift regression; no broad tooling tests are repeated.

The final integration needed a narrow splitter repair: exact hidden bodies
spanned multiple incbin fragments around symbolized literals. Reviewed
replacement endpoints for 08232F1C and 08248E70 consume only those bodies,
leaving neighboring assembly intact. Five focused boundary/compiler tests
pass, including a regression that preserves a fragment crossing the endpoint.
This required tooling check is separate from the broad suite omitted above.

Final accepted-source head: `82d700d`. Both the original and restored complete
ROM builds print `build/boktai3.gba: OK`; all 35 shifted-data screenshots pass
(intro 16 / save 7 / menus 12). All exacts are separately committed for one
combined integration. The 65 unresolved candidates remain local and ignored.
A source-only local archive preserves 519 candidate files, including duplicate
and already-matched drafts; it is not available in a GitHub clone.
