## The ROM

Each arm of `if (b->sprite.flags & 4)` loads `ldr r3, =0x0403B714` first, then
inlines the random read into angle (r4). Speed is in r5. Later, r4 is `&pos`, r5 is
the hoisted 0x3FF mask and r6 is the table. The origin is a dead constant. Its load
survives because combine folds its only use and leaves a `(use)` insn.

## Why the priority route is closed

Setup must survive a join with two sets. A single block-local origin is either
deleted (z2) or folded into the table load (x1, xa). With the use right after the
join (the speed read, z3), the origin loads are deleted as well. That leaves the
v->y read, about 88 insns later, as the only place a use keeps both loads. With 3
refs, no length there comes near angle's 3000. So setup cannot get r3 by priority.
What remains is to keep angle and speed off r3 another way: a preference, or a
conflict.

x1 is worth a look. There angle does land in r4, because a pseudo local to the arm
(the table, after combine) takes r3 first in local-alloc. The ROM has the origin in
that place, not the table.

## The priorities, read from the dumps (second pass)

The pseudo is `setup` (pseudo 30). In w_0 the allocation dump shows:

* 3 refs: two sets and one `(use)`.
* Flow live length 88. At allocation it is 352, because REG_EQUIV doubles it twice.
* Priority 85.

Its rival `angle` (pseudo 28) has 6 refs, live 40 and priority 3000, and conflicts
only with r0 to r2.

The `(use)` comes from combine's `distribute_notes`. Combine folds
`address - origin` in the v->y read and moves the REG_DEAD note backward. It finds
no other reference before the head of the block, so it emits `(use (reg 30))` at
that head: label 249, just after v->z's Debris_Scale. That is why setup lives from
the arms to there.

The ROM agrees. r3 is untouched from 0x2E to 0xFC, where the v->y read first
reuses it. So the ROM's setup has the same life as w_0's. To be allocated before
angle with 3 refs, it would need a live length at allocation under 10. Even without
REG_EQUIV the flow length is 88, which gives 340.

Pushing angle below 85 the other way would need a live length over 1400. No loops
are involved, so loop-depth weighting doesn't apply.

**Conclusion:** no C ordering of references and lives can produce the ROM's order
through priority. The ROM must keep angle off r3 through `regs_someone_prefers` (a
lower-ranked conflicting pseudo that prefers r3) or through a hard-register conflict.
The knob match is consistent with this. It shows what ordering is needed, not that a
priority change is reachable.

## What a preference would need (agbcc global.c)

Angle's first pass would skip r3 if a lower-priority pseudo that conflicts with it
preferred r3 (`regs_someone_prefers`, built in `prune_preferences`). Preferences come
only from `set_preference`, called from `mark_reg_store` with a register set and its
source. Either the source is a register, or its first operand is one: a hard register,
or a pseudo local-alloc has already placed. For setup that means an insn that sets
setup from r3, or one that sets r3 (or a local in r3) from `setup + ...`. Both of
setup's sets load a constant, and combine folds its one use away. So setup as written
can't carry a preference, and the lever has to be a different pseudo that prefers r3
and conflicts with angle. A hard r3 live inside angle's life would also work, but no
call falls inside angle's life (the last use of angle is v->z).

**What one preference would fix.** If setup alone preferred r3, find_reg would
produce the ROM's order. Angle would skip r3 because a lower-ranked conflicting pseudo
prefers it, and take r4. Speed (1153) would skip r3 for the same reason and take r5.
Setup would then get r3. In the ROM, r3 is never read between the arms and 0xFC, so
the preference can't come from a surviving use. It has to come from a set: setup
copied from a local that local-alloc put in r3, a copy final then deletes as a no-op.

I tried building setup from a value only combine can fold (`ORIGIN +
((u8)b->sprite.flags >> 8)`, the `| ((u8)gRandomIndex >> 8)` form, a block-local copy;
r1 to r4). This removes the REG_EQUIV doubling, as fact 231 predicts: priority 340,
live 88. But combine folds the copy, so no preference survives, and the first arm's
origin load is lost (22 to 23 insns).

**One assignment before the if** (u/v variants). Here setup is assigned once before
the if, and each arm reads relatively through it. The arm read is either
`ParticleRandom_ReadRelativeSample(setup, (const u16 *)RANDOM_TABLE_ADDR)` or the
gRandomTable form.

* With a plain constant, cse folds it (24 or 49 insns).
* With `ORIGIN + ((u8)b->sprite.flags >> 8)` it does what was predicted. Combine
  emits `(use (reg 30))` at the head of each arm, the live length drops to 23 and
  the priority rises to 1304 (v_relL_1, 22 insns).

But the one set before the if has a constant REG_EQUIV, so the pseudo is
eliminated: no `ldr =0x0403B714` is emitted at all, in the arms or before the if.
The ROM needs the load inside each arm.

To get both a short life and the in-arm loads, the set must be in the arm, with a
block boundary between it and the folded use. The ROM's arms contain no branch, so
I found no C that does this.

**Why the speed-read use disappears (z3).** gcse's CPROP pass 1 logs `CONST-PROP:
Replacing reg 30 in insn 142/148`. Both arms' sets hash to one SET-table entry, so
the constant counts as available at the join (BB5), and cse2 then deletes the sets.
In w_0 the use sits in BB11, after Debris_Scale's branches, and CPROP makes 0
constant substitutions there. So the v->y read is the earliest place a folded use
keeps the arm loads. That agrees with the ROM's r3 staying untouched to 0xFC, and it
fixes setup's life at what w_0 has.

**Copy from a local, to get a preference** (k1 to k8). In each arm:
`u32 origin = ...; gRandomIndex = ...;`, a ReadSampleAddress read through origin, and
`setup = origin;` placed either before or after that read. The intent was to let
origin live across the index advance and take r3 in local-alloc, so that setup
inherits a preference for r3.

* With the plain constant (k5 to k8: 22 to 47 insns, best k7), cse rewrites
  `setup = origin` as `setup = const`. That moves setup's load below the index
  store, and no preference survives.
* With the u8 >> 8 form (k1 to k4: 25 to 49), the origin is folded the same way.

The setup in r5, angle in r3 order is unchanged in every one.
