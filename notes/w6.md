# w6 notes

## Skipped (not matched)

- 081D53B4 (6+ attempts): size and branch layout match. The difference is
  register choice. The original loads the offset constant into r1 and keeps the
  pointer in r0 (`ldr r1,[pc]; adds r0,r4,r1; ldr r1,[r0,#8]`). agbcc gives the
  constant r0 and the pointer r2.
- 081D5444 (4+ attempts): size matches. `*(u16*)(p+0xD4E) |= 1` gets the offset
  constant in r0 and the pointer in r2. The original keeps the pointer in r2 and
  computes `1 | v` in r0. Temps and explicit pointers gave the same code.
- 081F0208 (3 attempts): the original loads the table pointer 0x08613E00 before
  reading p[0xAC]. agbcc computes the index first. Declaration order did not change
  the output.
- 081F065C: the literal pool holds the thumb address of sub_081F05D0 (bit 0 set).
  A C function pointer relocates to the even address, so the pool word differs.
  Tooling: no way to emit a thumb-tagged function pointer from C.
- 081E4174, 081E44D4, 081E9D10: tooling. The C object emits its own literal pool,
  but split.py keeps the original pool as trailing asm (`_081E4184: .4byte`), so
  the ROM grows by 4 bytes and later BL targets shift (first diff reported at
  0x08001482 in AgbMain). The same pattern shows up for any function whose pool
  sits after its last instruction and is followed by an asm label.

## Tooling problems

- build.py reports the first differing byte, which is usually a far BL in AgbMain
  (0x08001482) whenever any C function changes size. Per-function checks need a
  manual disassembly diff.
- A C literal pool after the function is duplicated (see above).
- Function pointers in C cannot produce the thumb bit (see 081F065C).
